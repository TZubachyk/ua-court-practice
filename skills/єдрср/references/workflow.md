# Workflow: процедура виконання запиту

Цей файл деталізує крок-за-кроком, як скіл виконує запит. Використовується SKILL.md як референс.

---

## Фаза 1. Уточнюючі питання

### Шаблон фраз

Привітання й опис плану (1–2 речення):
> «Шукаю в ЄДРСР з пріоритетом до перевірки повного тексту, додатково використовуватиму офіційні постанови ВС і дайджести. Кожне рішення верифікуватиму перед включенням у таблицю. Перед стартом — кілька уточнюючих питань (можна відповідати скорочено).»

Питання (всі 8, нумеровано):
1. Тема й контекст: яка норма / інститут? Які конкретні питання має дати відповідь практика?
2. Юрисдикція й інстанції: господарська/цивільна/адміністративна; перша/апеляція/касація; конкретний суд (пріоритет)?
3. Часовий діапазон? (дефолт: 2020 — сьогодні)
4. Кількість рішень? (дефолт: до 15)
5. Стовпці таблиці? Дефолт: `Реквізити (номер, дата, суд) + посилання на ЄДРСР | Позиція суду + мотиви з цитатами та локаціями`. Додати щось?
6. Аналітичний текст перед таблицею потрібен? (дефолт: тільки якщо є конкретні питання у запиті)
7. Методологія / застереження в кінці? (дефолт: ні)
8. Назва файлу? (дефолт: `{YYYY.MM.DD} - {коротка тема}.docx`)

### Дозволені формати відповідей

- Розгорнутий («1. ст. 50 ГПК, ситуація: ...; 2. госп, перша + ВС; 3. 2022-2026...»)
- Скорочений («1 ось так; 2 так; 3 дефолт; 4 5 справ»)
- Часткові («тільки 5 і 8») — на решту застосовуй дефолти.

### Підсумок розуміння

Після отримання відповідей — 2-3 речення підсумку:
> «Розумію задачу так: шукаю практику [норма/інститут] у [інстанції] за [період], кількість [N], стовпці: [список]. Аналітика [потрібна/не потрібна]. Стартую пошук.»

## Фаза 2. Пошук

### Жорсткий порядок джерел

1. **ЄДРСР** — https://reyestr.court.gov.ua/
2. **supreme.court.gov.ua** — постанови ВС, дайджести
3. **Дайджести судової практики ВС** — court.gov.ua/userfiles/media/
4. **Дзеркала** — clarity-project, youcontrol, iplex, protocol, verdictum (для лідів)
5. **Фахові публікації** — protocol.ua, advokatpost.com, yur-gazeta.com, yvu.com.ua (тільки як стартова точка, ніколи як основне джерело тверджень)

### Стратегія пошуку

**Спершу** збери 3-5 пошукових запитів з ключовими словами теми. Запусти їх паралельно (через WebSearch).

**Далі** для кожного перспективного результату:
- Якщо це лінк на ЄДРСР — фетчиш повний текст (див. фазу 3).
- Якщо це лінк на дзеркало — витягуєш reg-номер і фетчиш текст з ЄДРСР.
- Якщо це лінк на фахову публікацію — витягуєш номер справи, шукаєш у ЄДРСР, фетчиш текст.

**Не зупиняйся** на першому знайденому. Перевір 2-3 додаткові запити з варіаціями ключових слів, щоб не пропустити релевантне (особливо якщо тема рідкісна).

### Коли ЄДРСР блокує (CAPTCHA, порожній результат)

1. Йди в дзеркала (clarity-project найкраще).
2. З дзеркала витягуй reg-номер.
3. Прямо фетчиш `https://reyestr.court.gov.ua/Review/{reg-номер}` — там часто видає текст напряму.
4. Якщо і це не працює — попроси користувача надіслати текст рішення в чат.

## Фаза 3. Верифікація

### Як читати повний текст (curl-first, двоетапний парсер, v0.3+)

**WebFetch для повного тексту рішень — ЗАБОРОНЕНИЙ** (правило 9 у SKILL.md). WebFetch повертає реконструйований текст через вторинну модель, яка вигадує мотиви і цитати.

Використовуй **тільки** `curl` + двоетапний парсинг — див. SKILL.md, Крок 4.1 (Етап A + Етап B). Коротко:

1. **Етап A**: `curl` завантажує HTML → Python чистить теги → виводить карту секцій (позиції заголовків «Позиція ВС», «МОТИВИ», «Висновки» тощо) + реквізити. Для рішень ≤25K символів — виводить повний текст одразу.
2. **Етап B** (тільки якщо >25K): запитуєш конкретну секцію за ключовим словом з контекстом ±3000 символів або за позицією секції з карти.

Перевіряй отриманий текст:
1. Чи output містить вступну частину з реквізитами справи (суд, дата, номер справи)?
2. Чи містить мотивувальну частину з пунктами / абзацами?
3. Чи містить резолютивну частину з постановою / ухвалив суд?

Якщо output виглядає підозріло коротким або «NOT FOUND» — пробуй дзеркало (clarity-project) через `curl`, або проси користувача надіслати текст.

### Перевірка релевантності

Для кожної кандидат-справи спитай себе:
- Чи рішення стосується саме того питання, що поставив користувач? (Не «дотично», не «загалом про той інститут».)
- Чи в мотивувальній частині є **буквально та позиція**, яку ти хочеш приписати рішенню в таблиці?
- Чи цитата, яку ти хочеш дати, ДОСЛІВНО присутня в тексті?

Якщо хоча б на одне «ні» — або справа не входить, або цитату треба переписати з оригіналу.

### Маркер впевненості

Постав:
- ✅ якщо ти прочитав повний текст у ЄДРСР і вся інформація для таблиці витягнута звідти буквально.
- ⚠ якщо текст у ЄДРСР не дочитав, але справа підтверджена надійним вторинним джерелом (supreme.court.gov.ua, офіційний дайджест ВС, фахова публікація з конкретною цитатою).
- ❌ якщо є сумнів. ❌-справи **не йдуть у таблицю**.

## Фаза 4. Генерація Word-файлу

### Структура документа

```
Заголовок (центр, 18pt, жирний)
Підзаголовок (центр, 16pt, жирний)

[Якщо запитали аналітику]
Аналітичний текст з відповідями на конкретні питання,
з посиланнями на справи з таблиці.

[Якщо є питання — підзаголовки H1 для кожного]

Таблиця судової практики (з шапкою D9E2F3)

[Якщо запитали методологію]
Примітки / Методологія
```

### Параметри документа

- Формат: A4 (11906 × 16838 DXA)
- Поля: 1″ зверху/знизу/ліворуч, 0.75″ праворуч (для ширшої таблиці)
- Шрифт: Times New Roman
- Розмір: 14pt основний, 11pt у таблиці, 18pt заголовок, 16pt підзаголовок
- Інтервал: 1.5 у тексті, 1.3 у таблиці
- Таблиця: ширина = 9360 DXA (по полях), внутрішні поля комірок 100/120 DXA
- Гіперлінки: колір #0563C1, підкреслені
- Маркер впевненості: ✅ зеленим (#006100), ⚠ жовто-помаранчевим (#BF8F00)
- Шапка таблиці: фон #D9E2F3, текст жирний по центру

### Перевірка згенерованого файлу

Після генерації:
```bash
unzip -p file.docx word/document.xml | grep -c '<w:tr>'
# має дорівнювати кількості справ + 1 (шапка)
unzip -p file.docx word/document.xml | grep -c '<w:hyperlink'
# має дорівнювати кількості ✅-справ (для ⚠ лінків немає)
```

## Фаза 5. Звіт

Тільки фінальний звіт (без поетапних апдейтів):

```
Готово. Файл [{назва}.docx]({назва}.docx)

У таблиці {N} справ: {N_verified} зі статусом ✅ верифіковано та {N_secondary} зі статусом ⚠.

Що потребує перевірки в ЄДРСР:
- Справа № X (...) — reg-номер встановлено за вторинним джерелом, в реєстрі прямою перевіркою не підтверджено.
- ...

[Опціонально: ключові висновки, які випливають з практики]
```

## Фаза 6. Ітеративна підтримка

### «Перевір справу X»

1. Попроси користувача надіслати повний текст рішення у чат (якщо немає).
2. Порівняй буквально кожне твердження з таблиці / аналітики з оригіналом.
3. Якщо є розбіжності — відкрито про них скажи, запропонуй точні правки.
4. **Не вноси правки в файл, доки користувач не підтвердив.**

### «Додай ще N справ»

1. Розширюй пошук (інші ключові слова, ширший період).
2. Валідуй так само, як основний пакет.
3. Додай у таблицю — пере-генеруй файл повністю (не патчуй XML).

### «Заміни справу X на іншу»

1. Поясни мотив заміни (якщо твій).
2. Знайди заміну, валідуй.
3. Пере-генеруй файл.

### «Зауваження від ментора»

1. Уважно інтерпретуй — що саме ментор питає / просить виправити.
2. Якщо ментор просить новий зріз практики (як «чи зустрічав ухвал ГСМК про X») — створи окремий файл під цей зріз, не змішуй з основним.
3. Якщо ментор сумнівається в позиції / цитаті — повернись до фази 3 верифікації.
