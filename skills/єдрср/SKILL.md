# Скіл «ЄДРСР» — пошук і верифікація української судової практики

## Призначення

Знайти релевантну судову практику з ЄДРСР (https://reyestr.court.gov.ua/), перевірити кожне рішення за його **повним оригінальним текстом** і скласти Word-документ із таблицею перевірених справ.

## Активація

Скіл активується автоматично, коли користувач просить знайти/підібрати:
- судову практику, релевантну судову практику, позиції судів
- практику ВС, КГС, КЦС, КАС
- рішення в ЄДРСР
- таблицю судової практики
- аналіз / огляд / підбірку рішень

Також активується для англомовних запитів про українські суди.

## АНТИ-ГАЛЮЦИНАЦІЙНІ ПРАВИЛА (НЕОБХІДНІ)

Ці правила не можна порушувати ні за яких обставин:

1. **Заборонено цитувати або парафразувати зміст рішення без прочитання повного оригінального тексту цього рішення.** Якщо ти не бачив повний текст конкретного рішення в поточному контексті — ти не маєш права писати, що в ньому є.

2. **Заборонено приписувати рішенню правову позицію, якщо її буквально немає в оригіналі.** Навіть якщо ця позиція «логічно випливає» зі справи або згадується у вторинних джерелах — це не дозволено.

3. **Заборонено використовувати підсумовуючі сервіси** (як-от WebFetch з промптом «дай резюме», вторинні огляди статей, реферативні видання) **як джерело тверджень про мотивувальну частину рішення**. Підсумовуючі моделі регулярно вигадують зміст судових рішень. Підсумовуючі сервіси можна використати лише для **пошуку лідів** (виявлення кандидатів-справ), але далі ти зобов'язаний пересвідчитися в оригінальному тексті в ЄДРСР.

4. **Якщо повний текст недоступний** (ЄДРСР блокує, дзеркала недоступні, ipLex не віддає тіло) — попроси користувача надіслати текст рішення у чат і чекай. Не вигадуй, не виводь зі схожих справ, не використовуй пам'ять.

5. **Кожна справа в таблиці повинна мати маркер впевненості:**
   - ✅ **Верифіковано в ЄДРСР** — ти прочитав повний текст рішення в ЄДРСР і всі цитати/висновки в таблиці походять буквально звідти.
   - ⚠ **Знайдено у вторинному джерелі / потребує перевірки в ЄДРСР** — справа знайдена в надійному вторинному джерелі (supreme.court.gov.ua, дайджест ВС, фахова публікація), reg-номер встановлено за вторинним джерелом і не пройшов прямої валідації в ЄДРСР.
   - ❌ **Не верифіковано** — цитата є під сумнівом, або повний текст не вдалося отримати. Такі рішення в таблицю **не включаються**, доки користувач не надасть текст.

6. **Гіперлінк у таблиці завжди веде на reyestr.court.gov.ua/Review/{reg-номер}.** Якщо reg-номер не валідовано — посилання НЕ ставиться, а в стовпці маркується «потребує перевірки в ЄДРСР».

7. **Кожна цитата в таблиці має локацію в тексті оригіналу:** «п. X.Y», «абз. N п. X», або «розділ "Позиція Верховного Суду", абз. N» — якщо нумерації немає.

8. **Заборонено генерувати reg-номери з пам'яті** або «вгадуючи з діапазону дат». Reg-номер береться тільки з прочитаного джерела.

9. **WebFetch на reyestr.court.gov.ua часто повертає РЕКОНСТРУЙОВАНИЙ текст** (вторинна модель «дописує» те, що могло б бути в постанові). Це класична галюцинація — навіть коли результат виглядає правдоподібно і містить «номери пунктів». **НЕ довіряй WebFetch для повного тексту судових рішень.** Завжди верифікуй через прямий `curl` (див. Крок 4 нижче) — у сирому HTML ЄДРСР тіло рішення є всередині captcha-обгортки, його можна витягти регулярками.

10. **PDF-огляди судової практики ВС (supreme.court.gov.ua, court.gov.ua) — читати ТІЛЬКИ через `pdftotext`, а не WebFetch.** WebFetch для PDF повертає «не можу прочитати бінарний файл». Правильний шлях:
    ```bash
    # одноразово: brew install poppler
    curl -sL "URL.pdf" -o /tmp/digest.pdf
    pdftotext -layout /tmp/digest.pdf - | grep -i -B1 -A8 "ключове слово"
    ```

11. **Якщо джерело блокує (HTTP 403, CAPTCHA, порожнє тіло) ТРЕТІЙ раз поспіль для конкретної справи — одразу проси користувача надіслати текст у чат.** Не штовхайся через ще 5 дзеркал — це лише втрачає час.

8. **Назва вихідного файлу** (дефолт: `{YYYY.MM.DD} - {коротка тема}.docx` у поточній робочій теці).

Після отримання відповідей — підсумуй у 2–3 реченнях, як зрозумів задачу, і починай пошук без додаткових питань.

### Крок 4. Верифікація кожного кандидата (curl-first)

Для кожної знайденої справи дотримуйся ЦЬОГО порядку джерел (не WebFetch!):

**4.1.** **Перший крок — Bash + curl на ЄДРСР з парсингом сирого HTML.** WebFetch для reyestr.court.gov.ua — заборонений для повного тексту (див. правило 9).

Процес складається з **двох етапів**: спочатку отримати карту секцій рішення, потім витягти потрібні секції.

**Етап A. Завантаження + карта секцій:**

**Етап B. Витягування конкретної секції** (тільки для довгих рішень >25K):

```bash
        end = min(len(full), pos + 3000)
        print(f'=== HIT {i+1}/{len(hits)} at char {pos} ===')
        print(full[start:end])
        print()
else:
    print(f'Keyword "{keyword}" not found in text')
    # Фолбек: секція від позиції до +10K
    section_start = {позиція_з_карти}  # число з Етапу A
    print(full[section_start:section_start+10000])

```

**Коли який етап:**
- **Рішення ≤25K символів** → Етап A виводить повний текст, Етап B не потрібний
- **Рішення >25K символів** → Етап A дає карту секцій і реквізити. Далі запускай Етап B з ключовим словом із запиту користувача (наприклад, `"заінтересована особа"`, `"охоронюваний законом інтерес"`). Якщо потрібна конкретна секція — підстав її позицію з карти

**Після обробки** кожної справи — видали тимчасовий файл: `rm -f /tmp/rev_{reg-номер}.html`

Сирий HTML ЄДРСР містить тіло рішення прямо в DOM (всередині captcha-обгортки). Цей шлях обходить захист і дає буквальний текст.

**4.2.** Якщо `curl` повернув HTML без тіла («NOT FOUND») — **пробуй Playwright** (якщо встановлено). Playwright обходить JS-блоки і CAPTCHA, які ламають curl:

```bash
python3 << 'PYEOF'
import re
try:
    from playwright.sync_api import sync_playwright
except ImportError:
    print("PLAYWRIGHT NOT INSTALLED — skip to step 4.3")
    exit(1)
url = "https://reyestr.court.gov.ua/Review/{reg-номер}"
with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()
    page.goto(url, wait_until="networkidle", timeout=30000)
    html = page.content()
    browser.close()
text = re.sub(r'<script.*?</script>', '', html, flags=re.DOTALL)
text = re.sub(r'<style.*?</style>', '', text, flags=re.DOTALL)
text = re.sub(r'<[^>]+>', ' ', text)
text = text.replace('&nbsp;',' ').replace('&quot;','"').replace('&#39;',"'").replace('&amp;','&')
text = re.sub(r'\s+', ' ', text).strip()
m = re.search(r'ПОСТАНОВ[АИ] ІМЕНЕМ|РІШЕННЯ ІМЕНЕМ|УХВАЛА|ПОСТАНОВЛЕНИЕ ИМЕНЕМ|РЕШЕНИЕ ИМЕНЕМ|ОПРЕДЕЛЕНИЕ', text)
if m:
    full = text[m.start():]
    print(f'=== PLAYWRIGHT: РІШЕННЯ ЗНАЙДЕНО ({len(full)} символів) ===')
    if len(full) <= 25000:
        print(full)
    else:
        with open('/tmp/rev_{reg-номер}.html', 'w') as f:
            f.write(html)
        print(f'Текст довгий — збережено в /tmp/rev_{{reg-номер}}.html, використай Етап B')
        for pattern in [r'Позиція Верховного Суду', r'МОТИВИ:', r'Висновки суду', r'ПОСТАНОВИВ:']:
            for match in re.finditer(pattern, full, re.IGNORECASE):

else:
```

**4.3.** Якщо ні curl, ні Playwright не дали тіла рішення — **ОДРАЗУ попроси користувача надіслати текст рішення у чат**. Не пробуй ще інші ресурси. (Це правило 11.)

**4.4.** Для PDF-оглядів ВС — **тільки `curl + pdftotext`** (правило 10). WebFetch для PDF — заборонений.

**4.5.** Для коротких рішень (≤25K) — читаєш повний текст одразу. Для довгих (>25K) — читаєш карту секцій з Етапу A, потім запитуєш конкретну секцію через Етап B з ключовим словом із запиту користувача. Обробляй справи **послідовно** — не тримай 10 повних текстів у контексті одночасно, зберігай лише витягнуті цитати і переходь до наступної справи. Виокрем ТІЛЬКИ ті фрагменти, що буквально відповідають питанню користувача. Локалізуй кожну цитату («п. 4.4», «абз. 3 п. 12», «розділ "Позиція Верховного Суду"»).

**4.6.** Постав маркер впевненості (✅ / ⚠) — див. правило 5.

**Якщо знайдена справа НЕ підходить за змістом** — викинь її, не намагайся «натягнути» позицію, якої немає в тексті.

### Крок 5. Генерація Word-файлу

Використай шаблон `scripts/generate-docx.js` як стартову точку. Адаптуй:
- стовпці таблиці — згідно з відповідями користувача;
- структуру документа: заголовок → (аналітичний текст, якщо запитували) → таблиця → (методологія, якщо запитували);
- параметри: A4, Times New Roman, 14 pt текст, 11 pt таблиця, 1.5 інтервал, поля 1 дюйм (2,54 см), кольорове маркування ✅/⚠ за бажанням.

Перевір валідність файлу: розпакуй .docx, перевір кількість рядків таблиці = заголовок + кількість справ; кожна справа має робочий гіперлінк на ЄДРСР (для ✅) або позначку «потребує перевірки» (для ⚠).

### Крок 6. Звіт користувачу

Подай **тільки фінальний звіт** (без поетапних апдейтів) з:
- посиланням на створений файл (markdown-лінком);
- коротким описом того, що в таблиці (кількість справ, скільки ✅ і скільки ⚠);
- явним переліком справ, що мають маркер ⚠ — з поясненням, що саме потребує перевірки.

### Крок 6.1. Автоматичний запуск суб-агента верифікації

**ОБОВ'ЯЗКОВИЙ КРОК.** Після видачі фінального звіту — завжди спавни суб-агента верифікації у фоновому режимі. Це дає другу спробу знайти рішення, які ти не зміг отримати з ЄДРСР через CAPTCHA, тайм-аути або інші блоки.

```
Agent({
  subagent_type: "general-purpose",
  description: "ЄДРСР верифікація — дотягування невалідованих справ",
  run_in_background: true,
  prompt: `Ти — суб-агент верифікації судових рішень.

КРОК 1: Прочитай скіл верифікації:
Read файл: {абсолютний шлях до репо}/skills/єдрср-верифікація/SKILL.md

КРОК 2: Виконай верифікацію документа за інструкцією зі скіла.

Документ для верифікації: {абсолютний шлях до .docx}

Справи зі статусом ⚠ (потребують дотягування):
{для кожної ⚠-справи: номер справи, суд, дата, що відомо з вторинних джерел}

Справи зі статусом ✅ (контрольна перевірка):
{для кожної ✅-справи: номер справи, reg-номер з гіперлінку}

Контекст документа (тема, юрисдикція, ключові слова для пошуку):
{коротке резюме теми документа}`
})
```

**Що передавати суб-агенту:**
- Абсолютний шлях до репо (щоб він міг прочитати SKILL.md верифікації)
- Абсолютний шлях до згенерованого .docx файлу
- Повний перелік ⚠-справ із номерами, судами, датами
- Повний перелік ✅-справ із reg-номерами
- Коротке резюме теми (для пошукових запитів)

**Що робити, коли суб-агент повернеться:**
- Повідомити користувача про результати верифікації
- Якщо є оновлений `_verified.docx` — повідомити про нього
- Якщо є розбіжності в цитатах — показати їх користувачу

### Крок 7. Ітеративна підтримка

У продовженні розмови підтримуй такі типи запитів:
- **«перевір справу X»** — отримай повний текст від користувача чи з ЄДРСР, звір моє резюме з оригіналом, дай чесний звіт про розбіжності.
- **«додай ще N справ»** — продовжи пошук, валідуй так само, додай до таблиці.
- **«заміни справу X на іншу»** — поясни мотиви (якщо твої), знайди заміну, валідуй, заміни.
- **«у мене зауваження від ментора: ...»** — інтерпретуй, перепланіруй роботу, виконай.

## Бюджет роботи і зупинка

Скіл не повинен «штовхатися» через десятки запитів, коли джерела блокують. М'які ліміти:

- **30 пошукових/фетч-запитів сумарно** (WebSearch + WebFetch + Bash curl) — після цього проведи інвентар: скільки ✅-справ маєш.
- **Якщо ✅ < 3 після 30 запитів** — зупинись, скажи користувачу: *«У відкритих джерелах для верифікації знайшов N справ; реєстр і дзеркала блокують. Дайте, будь ласка, тексти X, Y рішень у чат, або я завершу таблицю з тим, що маю».*
- **Якщо ✅ ≥ 3, але далі не йде** — завершуй з тим, що є. Краще менша, але якісна таблиця, ніж погоня за 15 справ через дзеркала з ризиком галюцинації.
- **Не повторюй те саме джерело більше 2-3 разів** з варіаціями запиту. Якщо WebSearch на конкретну ключову фразу не дав ліда — переформулюй, не повторюй.

## Режими роботи

### Стандартний (за замовчуванням) — з прогрес-чеклістом

Людина, яка чекає 10-20 хвилин без жодного апдейту, починає панікувати і зупиняє процес. Тому **обов'язково виводь прогрес** на кожному ключовому етапі. Формат — короткий, інформативний, без зайвої болтанки:

**Після уточнюючих питань:**
```
Зрозумів задачу. Шукаю практику щодо [тема] у [юрисдикція] за [період].
```

**Під час пошуку (одне повідомлення, оновлюється):**
```
🔍 Пошук: знайшов N кандидатів, перевіряю повні тексти...
```

**Під час верифікації — рядок на кожну справу:**
```
Верифікація [1/8]: № 910/2059/20 — ✅ текст отримано, позиція підтверджена
Верифікація [2/8]: № 910/5028/21 — ✅ текст отримано, позиція підтверджена
Верифікація [3/8]: № 760/21858/16-ц — ⚠ реєстр блокує, пробую дзеркало... не вдалось
Верифікація [4/8]: № 910/13040/17 — ⚠ reg-номер не знайдено
...
```

**Перед генерацією файлу:**
```
Генерую документ: N справ (M ✅, K ⚠)...
```

**Після генерації — повний фінальний звіт** (як у Кроці 6).

**Правила прогресу:**
- Виводь рядок верифікації **ПІСЛЯ** обробки кожної справи, не до
- Не коментуй внутрішні рішення («зловив галюцинацію», «перемикаюся на curl») — просто роби правильно
- Не виводь повні тексти рішень або довгі цитати в прогрес — тільки статус
- Якщо справа займає більше 2 хвилин (дзеркала, повтори) — повідом про це: `Верифікація [3/8]: № X — затримка, пробую альтернативні джерела...`

### Дебаг (вмикається явно)

Якщо користувач каже *«у режимі дебаг», «коментуй процес», «розкажи що знаходиш»* — дозволено поетапні апдейти про знахідки, перешкоди, внутрішні рішення. Корисно для тестування скіла. Дебаг режим уточнюй, якщо запит виглядає тестовим («давай протестуємо», «прогоняємо на прикладі»).

## Шпаргалка операторів пошуку в ЄДРСР

Повна довідка — у `references/reyestr-search-rules.md`. Коротко:

- `AND` / `OR` / `NOT` — логічні
- `"фраза в лапках"` — точна фраза
- `*` — будь-яка кількість символів (мін. 3 перед)
- `?` — один символ
- `+термін` — обов'язковий термін
- `-термін` — виключити термін
- Фільтри: суд, регіон, ПІБ судді, форма судочинства, інстанція, тип документа, дата

## Що скіл НЕ робить

- Не пише плани вище 2 речень перед стартом роботи.
- Не дає поетапних апдейтів у бойовому режимі — тільки фінальний звіт.
- Не включає в таблицю справ зі статусом ❌.
- Не вигадує reg-номери, дати, склади суддів, цитати, локації.
- Не використовує WebFetch для повного тексту судових рішень (тільки curl + парсинг сирого HTML).
- Не використовує WebFetch для PDF-оглядів ВС (тільки curl + pdftotext).
- Не штовхається через десятки джерел, коли вже отримав 2-3 блоки поспіль для конкретної справи — просить текст у користувача.
- Не використовує інші джерела як підставу для тверджень про зміст рішення без прямого фетчу з ЄДРСР (або тексту від користувача).
